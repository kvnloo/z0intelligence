# z0int memory search (HC-2)

Benchmark harness for the HC-2 hill climb (see `/mnt/zer0models/workspace/zer0/data/operations/z19-research-20261105/REPORT.md`,
"z0int memory search"): make `z0int.memory.surface.search` fast without changing its results.

All fixtures under `fixtures/` are synthetic (generated by `generate_fixtures.py` from a fixed seed,
no owner text, no real credentials — only credential-shaped placeholders for scrub coverage).

## Reproducing

```bash
PYTHONPATH=src python3 benchmarks/memory_search/bench_search.py --label after
```

Builds an ephemeral AgentsView db + EventLog ledger from the frozen fixtures (sized up from the
reported ~1,605-event ledger to `event_payloads.json`'s 6,400 events, so the bottleneck the report
measured reproduces clearly on this machine before any fix), runs all 50 frozen queries through
`search()`, and prints p50/p90/max latency plus a combined hash of every query's ordered result
event ids. Per-query detail (including the full event id order) is written to `results/<label>.json`.

`capture_golden.py` was run once, against the unmodified code, to freeze `fixtures/golden.json`
(expected ordered event ids per query) and `fixtures/scrub_golden.json` (expected `scrub_text`
output per corpus entry). `tests/test_memory_search_equivalence.py` and the scrub byte-identical
test in `tests/test_memory_scrub.py` check the current code against those golden files — do not
regenerate them after the HC-2 change lands, that would defeat the point of the regression test.

| baseline_aa   | 50 | 309.163 | 353.216 | 415.713 | `92c6b68e...`  |
| scrub_change  | 50 | 288.030 | 328.280 | 490.451 | `92c6b68e...`  |
| after         | 50 |  92.883 | 128.982 | 316.846 | `92c6b68e...`  |
| after_aa      | 50 |  83.360 | 118.565 | 313.526 | `92c6b68e...`  |

Every label shares the same `combined_hash` — the HC-2 changes (scrub single-scan gating, then the
temporal mtime/size-keyed cache) never changed a single query's result set or order, only the time to
compute it. `after`/`after_aa` (same final code, run twice) land under the 100ms p50 target with
similar run-to-run noise to the baseline pair. See `results/*.json` for the full per-query rows.
